# reconcile alchemy activity subscriptions from postgres

each stack treats persisted credential accounts as its desired activity subscriptions and reconciles them into one active alchemy webhook per activity network. an anvil stack uses only anvil; every other stack uses each alchemy-supported network whose testnet classification matches the stack's chain. the subscription worker is the sole controller: it adopts the unique active address activity webhook matching the stack endpoint and network, creates one when absent, and stops when duplicates or an inactive existing webhook make ownership unsafe. reconciliation only adds missing accounts and runs during deployment checks and controller boot with the same failure behavior; checks disable queue consumption, while a running controller may process incremental jobs after webhook discovery and during repair. worker checks default to `60s` and accept an optional `${name}Timeout`; subscribe checks use `10m` on testnet stacks and `15m` on production stacks. new webhooks receive every account directly, while existing webhooks receive only accounts missing from their current address set. reconciliation limits itself to five alchemy management requests per second. both reconciliation and incremental jobs attempt every activity network before reporting their combined failures, and no other runtime mutates subscriptions when queueing fails. activity consumers discover webhook ids, signing keys, and networks from alchemy, bind each delivery to that registry, refresh it once after an unknown signature, and never rely on static single-webhook ids or keys. reconciliation warns at 90,000 accounts and fails at the 100,000-address limit. this favors boot and deployment repair over destructive synchronization, periodic repair, static webhook configuration, a per-network subscription ledger, or historical activity recovery; webhook sharding remains outside the design until the provider limit requires it.
